# #278 追加对账：完整快照改为只传差量

关联：<https://github.com/anywhere-labs/Agents-Anywhere/issues/278>

## 问题

完整快照（`timeline.sync`，`complete=true`）会替换整条时间线，所以以前只能整份放在一个请求里。DSH 的一个 62 MiB 会话超过了公网入口约 50 MiB 的上限，请求被 413 拒绝，永远上传不了。PR 291 只在 Connector 侧止血：被拒的会话被隔离为 `history_too_large`，其他会话照常同步，但这个会话的历史仍然看不到。

这个问题不只出现在 DSH。Pi 每个会话第一次同步都是完整快照；Codex 在条目被删除或检查点失效时，也会发送完整快照。而且只要删掉一个条目，就得把整个会话重新上传一遍。

## 参考：Claude Code Remote Control

调研了 Claude Code 2.1.296 的公开文档和本机二进制中的字符串。它们踩过同样的坑：v2.1.209 把整份对话记录放在创建会话的一个请求里，约 10 MB 时失败（anthropics/claude-code#78825），后来改掉了。RC 的对话记录只追加不改写：按 uuid 幂等，按条数和字节数分批上传，遇到 413 把这一批拆小重发，冲突时采用服务端的当前位置，读取全部用游标分页。

AA 的时间线是 runtime 原生历史的投影，会出现删除和重排，例如 Pi 切换分支、Codex 删除条目、DSH 的投影版本升级，所以不能照搬“只追加”。这里采用的是追加加对账，对应关系如下：

| RC | AA |
| --- | --- |
| 按 uuid 追加，重复写入不出错 | 按条目 ID 写入，内容和顺序都没变的条目，服务端直接跳过 |
| 客户端不知道服务端有什么时，用 `Last-Uuid` / 409 采用服务端的位置 | 先读服务端清单（ID、`orderSeq`、内容哈希），只传不同的部分 |
| 分批上传，每批有上限 | 差量走原来的增量分页，每页 8 MiB |
| 只追加，没有删除 | 增加 `timeline.delete`，只删除从清单里读到、快照中已经没有的 ID |
| 只回填最近 200 条 | **不采用**：AA 保留完整历史 |

## 协议

字段和语义见 [`docs/api/realtime.md`](../../api/realtime.md) 的 Reconciling complete snapshots 一节，这里只记录设计取舍：

- 新增 `POST /api/v2/connector/timeline/manifest`，分页返回服务端已存条目的 `(id, orderSeq, contentHash)`。
- `timeline.sync` 增加 `orderAuthoritative`：按 Connector 给的 `orderSeq` 写入，已有条目也照此调整。
- 新增 `timeline.delete`，用于删除条目。
- 删除条目、移动条目、插到中间都视为 reset：服务端设置 `timeline_reset_seq` 并发出 refetch，客户端用现有的重新拉取逻辑收敛。Web、Desktop、Android、iOS 都不用改。追加在末尾的条目仍然按普通的条目事件推送，大会话首次同步时可以逐步看到。
- 只删除从清单里读到的 ID。读完清单之后才写入服务端的条目不会被删，在这一点上比整份替换更安全。读清单前，服务端会先把这个会话写缓冲里已接受、尚未落库的实时条目落库，和整份替换一样，这些条目也能被删除。
- 一次对账是一个整体：先发差量，全部被接受后才发删除。差量有一页被拒，就不发删除；网络中断后重试，这个状态仍然保留。
- 完整快照按它在批次里的位置依次处理。前面的通知送达之后才读清单，所以同一批里的多个快照、前面的实时条目，都和依次整份替换的结果一致。
- 会话身份固定：清单、差量同步、删除都带同一个 `externalSessionId`，取自快照里第一个带 `source.sessionId` 的条目，也就是整份替换时服务端解析会话所用的那个 ID。带 `orderAuthoritative` 的同步按这个参数解析会话，不再看这一页恰好有哪些条目。所以没有变化时，发一个空的同步即可。
- 改写后的通知会替换原来的完整快照，留在待发队列里。网络中断后，从第一个未被接受的页继续，不会重新读清单，也不会重传已被接受的页。
- 兼容性：
  - 旧版 Server 对清单接口返回 404，Connector 就照旧整份发送，10 分钟后再试。
  - 新版 Server 在每个 ingest 响应里回执 `features: ["timeline.reconcile"]`。滚动发布时，如果对账的写入落到旧版 Server，响应里没有这个回执，Connector 就立即改为整份替换这个快照。
  - 旧版 Connector 继续发送完整快照，服务端照旧整份替换。
- DSH 插件等每个 ACK 最多 60 秒。relay 在 `snapshot.begin` 的 ACK 之前读取清单（命名快照的原生会话），并先发送会话元数据，因为条目必须先有所属的会话。如果会话处于隔离状态，元数据仍然报告不可用，也不改动“Host 最后报告的事实”。之后每一页的差量都在这一页的 ACK 之前上传完；commit 时只发送元数据和删除请求。遇到问题时（Server 没有清单、某一页被拒、页内条目指向别的原生会话），commit 时退回通用路径，由 ingest 客户端重新对账。DSH 插件和 bridge 协议都没有改动。

被放弃的方案是“分片暂存后一次性替换”，代码保存在 `git stash` 中（`issue-278: staged snapshot implementation`）。放弃的原因：它保住了原子性，但每次完整快照仍然要全量上传，服务端提交时还要在内存里拼出整份快照。

## 验证

环境：Windows 11，Python 3.12 / 3.13，Server 使用临时 SQLite，没有连接任何外部数据库或正式服务器。

- Server `tests/test_timeline_reconcile.py`：14 项通过。覆盖以下场景：
  - 清单分页，以及未建会话时返回空清单；
  - 清单接口需要 Connector 令牌；
  - 按顺序追加不触发 reset；
  - `orderAuthoritative` 移动已有条目、插到中间，都会触发 reset；
  - 删除只删除已知 ID，重复执行结果不变；
  - 畸形的删除请求返回 400；
  - 按清单对账的结果和整份替换一致；
  - 端到端：真实的 Connector ingest 客户端连真实的 Server 应用，中间加一个 256 KiB 上限的入口，首次同步约 1.2 MiB 的会话没有出现 413；再次同步时只上传了移动、编辑和新增的 4 个条目，并删除了 1 个；
  - ingest 响应回执 `features`；
  - 清单包含已接受但尚未落库的实时条目（去掉读清单前的落库后，这项测试会失败）；
  - 对账写入按 `externalSessionId` 解析会话：用服务端不认识的会话别名，加上正确的原生 ID，同步、清单、删除都能落到同一个会话；
  - 隔离期间重申 Host 的来源事实（带原来的时间），archived 保持不变；不带来源事实的 DSH 元数据会覆盖它。
- Server 原有的 `test_issue_278_snapshot_semantics.py`、`test_timeline_reconciliation.py`、`test_architecture_boundaries.py`：通过。
- Connector `tests/test_issue_278_reconcile.py`：24 项通过。覆盖以下场景：
  - 55 MiB 快照经过 50 MiB 入口同步到空的 Server，每个请求不超过 8 MiB；
  - 只上传变化的条目，删除已经没有的条目；
  - 内容没变时发送空的同步，并带上会话身份；
  - 差量被拒时不发删除，Server 上快照里还有的条目都不会被删；
  - 同一批里的多个快照和前面的实时条目，结果与依次整份替换一致；
  - 旧版 Server 接受了写入却没有回执 `features`，立即改为整份替换；
  - 重复 ID 保留最后的值；
  - 空快照会删除全部条目；
  - 跟随清单分页，删除请求分块发送；
  - 旧版 Server（返回 404）收到整份快照，10 分钟内不再询问；
  - 清单被拒绝时整份发送；
  - 清单服务暂时不可用时，快照留待重试；
  - 网络中断后从第一个未被接受的页继续，不重读清单；
  - DSH 边收边传，commit 只发送元数据；
  - DSH 再次同步时只上传修改、删除多余的条目；
  - DSH 某一页被拒时，退回通用路径对账；
  - DSH 的清单请求和每一页的同步、删除都带原生会话 ID；
  - 隔离期间，快照元数据仍报告不可用；Host 报告过其他事实时，元数据原样重申那条事实；
  - 一页没有回执就停止这次对账，并立即整份替换；
  - 条目指向多个原生会话、或有名无名混用时，整份发送；DSH 某页有无名条目时退回整份路径；
  - 因过大被隔离的 DSH 快照，在对账恢复后重新对账、解除隔离，恢复来源状态的通知带有效的 `observationOrigin`；
  - DSH 读清单前，先送出已排队的通知。
- PR 291 的相关测试（`test_bounded_ingest.py`、`test_bounded_sync.py`、`test_issue_278_dsh_snapshot.py` 等）：断言没有改，只是把 mock 换成会对清单接口返回 404 的“旧版 Server”（`tests/ingest_servers.py`）。另外，两个测试替身补上了读取清单的方法。
- 全量套件（审阅修复之后）：
  - Server 950 项通过，9 项失败；Connector 1205 项通过，92 项失败、6 个错误。
  - 逐项放到基线提交 `51041ebe` 上对比：这些失败在基线上同样出现，或者属于本来就时有时无的用例，单独重跑能通过。
  - 时有时无的原因已经查明：
    - Connector 的本机记录锁会把路径哈希成 49152–65535 的端口，落进 Windows 保留端口段时 bind 必定失败。这台机器上约 4.6% 的端口被保留，已经单独提出修复建议。
    - Server 锁统计的计时用的是 `time.monotonic()`，在 Windows 上只有 15.6 毫秒精度，很短的持锁时间会被量成 0。
- 本机测量（SQLite，没有网络开销），会话约 60 MiB：

  | 场景 | 27354 个约 2 KB 的条目 | 1250 个约 50 KB 的条目 |
  | --- | --- | --- |
  | 首次同步（Server 上是空的） | 4.5 秒，8 个请求，最慢 0.61 秒 | 2.5 秒，最慢 0.42 秒 |
  | 内容没变，再同步一次 | 1.3 秒，读清单 6 页共 1.2 秒，几乎不上传 | 0.4 秒，几乎不上传 |
  | 改 30 条、删 100 条 | 1.6 秒，上传 0.1 MiB | 0.6 秒，上传 0.1 MiB |

没有验证的部分：真实的 DSH Desktop 和 Nginx 闭环、PostgreSQL / Redis 部署、正式服务器上的耗时，以及 Web、Desktop、Android、iOS 客户端在对账过程中实际的显示效果（服务端发出的是这些客户端已有的 refetch 事件）。

## Pi 审阅

按用户要求，Pi（`gpt-6-astra`，xhigh，只读）审阅了最初的 4 个提交，提出 6 个 P0、1 个 P1、2 个 P2 和 2 个待确认项。逐条在代码中核对后：

| 问题 | 结论 | 处理 |
| --- | --- | --- |
| 差量被拒后，删除照样执行 | 成立 | 删除只在差量全部被接受后发送；重试后这个状态仍然保留 |
| 同一批的多个快照都读写入前的清单 | 成立 | 按顺序处理，前面的通知送达后再读清单 |
| 清单漏掉写缓冲里已接受、未落库的条目 | 成立 | 读清单前先进 session fence 把缓冲落库；新增的测试在去掉 fence 后会失败 |
| relay 显式传入的 `externalSessionId` 被丢掉 | 成立 | 直接读清单时保留显式参数 |
| 差量分页后可能解析到别的会话 | 成立（条目混用时） | 对账写入都带同一个 `externalSessionId`，服务端按它解析 |
| 锚点可能选中重复 ID 的旧值 | 成立 | 去掉锚点，没有变化时发空同步 |
| 滚动发布时，重排和删除被旧版静默吞掉 | 成立 | 响应回执 `features`，没有回执就立即整份替换 |
| 清单读取挤在 60 秒 ACK 内 | 有道理 | 每页 5000 条；DSH 改在 `snapshot.begin` 时读清单，和页面上传分开计时 |
| `orderSeq` 相同时两种路径排序不同 | 只在 `orderSeq` 重复时出现 | 不改，契约写明各条目的 `orderSeq` 应唯一 |
| 待确认：首页元数据重置隔离状态的 Host 事实 | 推演成立 | 改用不修改状态的改写，并加测试 |
| 待确认：Redis 多实例下的 reset 收敛 | 无法在本地验证 | 列入未验证 |

### 第二轮

Pi 用同样的设置复审了上述修复，确认按顺序处理、删除受差量约束、读清单前落库缓冲、去掉锚点这几处有效，没有新的 P0。新提出的问题，逐条核对后处理如下：

| 问题 | 结论 | 处理 |
| --- | --- | --- |
| 滚动发布时，旧版 Server 按差量条目自己的来源，把数据写进另一个会话 | 成立：需要快照混着多个来源 ID，并且正在滚动发布 | 快照条目指向两个以上原生会话时，整份发送，不对账 |
| DSH 实时刷新会把 `begin` 和后续页打包成一批，共用一个 ACK | 成立 | Connector 侧无法根治，写入已知局限 |
| 发现没有回执后仍发送剩余页；之后若有页被拒，就不再回退 | 成立 | 一发现没有回执就停止这次对账，整份替换；即使某页曾被拒也照样替换 |
| 回退整份发送遇到 413 后，同一份快照被永久跳过 | 成立 | 同一份被拒的快照，只要有清单就重新对账；没有清单时才只发元数据 |
| `quarantined_meta` 刷新时间戳，覆盖 Server 上较新的 archived | 成立 | Host 报告过其他来源事实时，元数据不带 `sourceState` |
| DSH 直接读清单时，没有等 Connector 队列里已排队的通知 | 成立（旧版非持久检查点路径） | 读清单前，在同一把发送锁下先把已排队的通知送出 |
| 测试只覆盖单页、隔离测试没有检查发出的来源事实、页大小常量的断言抓不住改动 | 成立 | 补充多页未回执、混合来源、对账恢复后重新对账、已排队通知、隔离元数据的测试，常量断言写明 5000；其中“已排队通知”和“多页未回执”两项，临时撤掉修复后会失败 |

### 第三轮

Pi 复审了第二轮的修复，没有发现 P0，确认多页未回执立即回退、对账恢复后重新对账、读清单前送出已排队通知这几处已经修好。逐条核对后处理如下：

| 问题 | 结论 | 处理 |
| --- | --- | --- |
| 第二轮去掉 `sourceState` 的修法引入回归：服务端会把不带来源事实的 DSH 元数据当成“当前时间的 available”，覆盖 archived | 成立，已用真实 Server 测试复现 | relay 保存 Host 最后报告的完整来源事实，隔离期间原样重申它（带原来的观察时间），服务端因此保留它；补充真实 Server 的测试 |
| 有名条目和无名条目混在一起时，差量可能只剩无名条目，旧版 Server 会按请求的 `sessionId` 写进另一个会话 | 成立 | 只有所有条目都指向同一个原生会话、或都不指向时才对账，否则整份发送；DSH 每页都要求所有条目指向快照的原生会话；撤掉这条规则后，对应测试会失败 |
| 读清单时一直占着全局发送锁，阻塞其他会话 | 成立 | 只在送出已排队通知时持锁，读清单时释放；DSH relay 在拿到清单之前，不会再为这个会话发送任何东西 |
| commit 成功后恢复来源状态的通知没有 `observationOrigin`，真实 Server 会整个请求返回 400；本地隔离记录在发通知之前就删掉了 | 成立（PR 291 遗留） | 补上 `observationOrigin: event`；通知发送成功或被永久拒绝后，才删除隔离记录；mock Server 也按真实规则校验来源 |
| ACK 那条已知局限的说明不完整 | 成立 | 补充等锁、送出已排队通知、begin 与 commit 可能同批，以及“只拆分 ACK 也无法解决读清单超时” |

## 已知局限

- 对账过程中，客户端可能看到中间状态：已上传的新条目先出现，删除在最后才生效。首次同步时，客户端会逐步看到历史。差量被拒时，这个会话只更新了一部分，错误照常上报，不会删除快照里还有的条目。
- 读取清单时，服务端需要逐行解析存储的 JSON 来取出 `contentHash`。条目很多的会话，读一次清单要花一些时间，见下文的测量。
- `orderSeq` 相同的条目，两种路径下的相对顺序都没有定义；各 runtime 需要给每个条目分配唯一的 `orderSeq`。
- DSH 插件对每个传输批次只等 60 秒。`snapshot.begin` 单独成批时，这 60 秒要覆盖：等待发送锁、送出已排队的通知、读完所有清单页。插件实时刷新时，`begin`、后续页，甚至 commit，都可能被打包进同一批，共用这 60 秒。读清单本身没有总时限，超时会导致整个 feed 失败并重新订阅。本机读一个 2.7 万条目的清单约 1.2 秒，但在慢服务器上仍可能超时。只把 ACK 拆成逐个操作，也解决不了清单本身超过 60 秒的情况，需要插件支持进度续期，或者另行设计读取预算。
- 条目指向的会话不一致（有的有 `source.sessionId`、有的没有，或者指向不同的会话）时，快照整份发送，过大时仍会被 413 拒绝。
- 一次对账里先有一页被拒、之后又遇到网络中断时，重试成功后不会再报告那次拒绝（删除仍会被拦下）。这和原有的分页发送行为一致。
- 按 `docs/versioning.md`，新增接口和通知属于 MINOR 更新，所有端要升到 2.1.0。本 PR 按要求暂不升版本号，发版时统一处理。
